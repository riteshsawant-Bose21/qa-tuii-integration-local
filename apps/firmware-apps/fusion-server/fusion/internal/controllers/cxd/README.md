# Digital Wall Controller Protocol Specification

## Transport
- Protocol: UDP
- Port: 9010
- Broadcast Address: 255.255.255.255 (or 192.168.1.255)

## Message Structure
All messages follow this basic structure:
```
[Header][Payload][Hash]
```

### Request Messages
Header format:
- GUID (16 bytes): Random session identifier, generated per request. Layout:
  - Data1 (4 bytes)
  - Data2 (2 bytes)
  - Data3 (2 bytes)
  - Data4 (2 bytes)
  - Data5 (6 bytes)
- Command (2 bytes): Command identifier, little-endian
- Payload Length (2 bytes): Length of following payload, little-endian

### Response Messages
Header format:
- Key (4 bytes): Generated by firmware, unique per response
- Command (2 bytes): Response command identifier, little-endian
- Payload Length (2 bytes): Length of following payload, little-endian

### Hash
- All messages end with a 20-byte SHA1 hash
- Hash is calculated over the entire message (header + payload)
- The hash does not include itself in the calculation

## Commands

### Get Current Settings
Request:
```
Command: CMD_QUERY (0xC101)
Payload: Empty (length = 0)
```

Response 1:
```
Command: RESP_QUERY (0x5501)
Payload Length: 116 bytes (0x0074)
Payload:
- Hardware ID (16 bytes): [4]uint32 array
- Current IP (4 bytes): IPv4 address
- MAC Address (6 bytes)
- DHCP Enabled (1 byte): 0x00 = false, 0x01 = true
- Static IP (4 bytes): IPv4 address
- Subnet Mask (4 bytes)
- Gateway (4 bytes): IPv4 address
- Model ID (8 bytes): Null-padded string (e.g., "CC2D")
- Serial Number (24 bytes): Null-padded string
- Name (40 bytes): Null-padded string
- Port (2 bytes): Little-endian
- Unknown (2 bytes): Usually 0x0000
```

Response 2:
```
Command: RESP_QUERY2 (0x5504)
Payload Length: 21 bytes (0x0015)
Payload:
- Hardware Tag (1 byte): 0xA0
- Hardware Length (1 byte): 0x10 (16)
- Hardware ID (16 bytes): Same as Response 1
- Operation Mode Tag (1 byte): 0xA1
- Operation Mode Length (1 byte): 0x01
- Operation Mode (1 byte): 0x01 = CSP
```

### Set Static IP
Request:
```
Command: CMD_SETUPNW (0xC102)
Payload Length: 108 bytes (0x006C)
Payload:
- Hardware ID (16 bytes): [4]uint32 array
- MAC Address (6 bytes)
- DHCP Enabled (1 byte): 0x00 = false, 0x01 = true
- Operation Mode (1 byte): 0x01 = CSP
- IP Address (4 bytes): IPv4 address
- Subnet Mask (4 bytes)
- Gateway (4 bytes): IPv4 address
- Model ID (8 bytes): Null-padded string
- Serial Number (24 bytes): Null-padded string
- Name (40 bytes): Null-padded string
```

Response:
```
Command: RESP_SETUPNW (0x5502)
Payload Length: 4 bytes (0x0004)
Payload:
- Result (4 bytes): 0x00000001 = success
```

### Reboot Sequence
1. Request Reboot Key:
```
Command: CMD_REBOOT (0xC103)
Payload Length: 40 bytes (0x0028)
Payload:
- Hardware ID (16 bytes): [4]uint32 array
- Reboot Config Key (24 bytes): All zeros
```

2. Receive Reboot Key:
```
Command: RESP_REBOOT (0x5503)
Payload Length: 40 bytes (0x0028)
Payload:
- Hardware ID (16 bytes): [4]uint32 array
- Reboot Config Key (24 bytes): Base64 encoded token
```

3. Return Modified Reboot Key:
```
Command: CMD_REBOOT (0xC103)
Payload Length: 40 bytes (0x0028)
Payload:
- Hardware ID (16 bytes): [4]uint32 array
- Reboot Config Key (24 bytes): Modified token
```

### Reboot Key Transformation
The reboot key received from the device must be transformed before being sent back:
1. Base64 decode the received key
2. Perform bitwise NOT operation on each byte
3. Base64 encode the result

## Data Types and Constants

### Hardware ID
- Fixed 16-byte identifier unique to each device
- Represented as 4 uint32 values in little-endian order
- Example: [0x51cec28e, 0x53393933, 0x38202020, 0xff113b15]

### Operation Modes
- CSP Mode: 0x01
- Known sizes:
  - Model ID: 8 bytes
  - Serial Number: 24 bytes
  - Name: 40 bytes

### String Fields
- All string fields are fixed length and null-padded
- ASCII encoding
- Trailing nulls should be trimmed when reading
- Strings shorter than field length should be null-padded when writing

## Protocol Notes
1. All multi-byte integers are little-endian
2. GUID is generated randomly for each session/request
3. Each response includes a unique key generated by the firmware
4. Device discovery requires handling both RESP_QUERY and RESP_QUERY2 messages
5. All messages are sent via UDP broadcast
6. The protocol uses fixed-size fields throughout
7. IP addresses should be IPv4 format

## Error Handling
- Messages with invalid hashes should be discarded
- Responses should be validated for correct command codes
- String fields should be validated for proper null-padding
- Network timeouts should be implemented for all operations
